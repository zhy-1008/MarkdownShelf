# P1.3 文件夹库初始化与检查

目录层、数据库层和使用权各回答一个问题。三个受管条目是否齐全，清单和数据库是否说的是同一个库，当前调用是否有权启用写入。`Library` 负责把这些判断按入口和时序组合起来。[V4.0 §3.1–3.4、§10.2](../specification/MarkdownShelf_Project_Design_v4.0.md)

## 类和对象的关系

| 类型或模块 | 职责与生命周期 |
| --- | --- |
| `Library` | 提供静态入口 `create`、`inspect` 和 `open`，编排校验、发布与开库。定义见 [library.h](../../src/core/include/markdownshelf/library.h)，调用链见 [library.cpp](../../src/core/domain/library.cpp)。 |
| `LibraryInfo`、`LibraryInspection` | 自有的值类型。前者保存规范化根路径、UUID、显示名、UTC 时间及版本，后者通过 `info` 表示检查成功。它们可以在会话关闭后继续读取。 |
| `LibraryLease` | 保存库 UUID、库根及父目录的守护句柄、根目录的物理 ID 和稳定文件锁。租约取得后暂由调用者拥有，`open` 只可消费一次。 |
| `LibrarySession` | 持有移交的租约、受管条目守护句柄和可写 `db::Connection`。显式 `close()` 和析构都先释放连接，再释放租约。 |
| `StagedDirectory`、`Directory` | Windows 私有实现。`Directory` 持有系统句柄、最终路径和物理身份。`StagedDirectory` 在单次创建期间管理暂存、原目标暂移、不可覆盖发布和失败清理。见 [Windows 文件实现](../../src/core/platform/library_files_win.cpp)。 |
| `LibraryError`、`LibraryManifest` | 前者提供稳定错误码、消息键、重试性、操作 ID 和可选恢复路径。后者是核心内部解析出的 UUID 和 UTC 时间值。见 [清单解析](../../src/core/domain/library_manifest.cpp)、[绑定](../../src/bindings/library.cpp)。 |

## 创建如何建立身份

`create(parent, name)` 从 Python 接收 `pathlib.Path` 和 `str`，在 C++ 中对应 `std::filesystem::path` 和仅在调用期借用的 UTF-8 `std::string_view`。父目录应存在并允许创建子目录，`name` 是单一合法 Windows 目录名。接口返回 `LibraryInfo`，失败抛出 `LibraryError`。

1. `create_library` 验证名称和父目录，确认目标为空或不存在，生成一次 UUID 和 UTC epoch 毫秒。Windows 文件名的保留名称、路径别名、共享方式及长路径都在平台层处理。
2. `StagedDirectory` 在同一个父目录下建暂存根。用 `CREATE_NEW` 创建主文件和清单。`initialize_database` 复用 P1.2 的迁移执行器执行 `0001_initial.sql`，再在事务中写入应用标识及绑定参数构成的单行元数据。CMake 将 SQL 嵌入核心，暂存扩展可在源码目录以外初始化。
3. 清单写入并刷盘后，用新的只读连接复查三个产物。`format_version=1` 说明如何解释 JSON，`application_id=0x4D53484C` 标识应用文件，`user_version=1` 选择 schema，UUID 标识具体是哪一个库。将 DB 中的 epoch 毫秒转为带毫秒和 `Z` 的文本，与清单核对同一时刻。索引版本和内容 epoch 初始为 `0`，活动 FTS 槽初始为空。
4. 发布前释放 SQLite 连接和子文件守护句柄。已有的空目标先按原句柄暂移，再次核对确实为空。整套库通过禁止覆盖的同卷重命名发布。因占用失败时，原目录按同一个文件 ID 还原，外部占据原路径时通过 `recovery_path` 报告原目录位置。暂存清理按本次创建记录中的文件 ID 执行。

## 检查与开库为何分开

`inspect(root)` 用 `resolve_directory` 取得实际根，核对 `assets/`、清单和主库文件。清单上限 64 KiB，通过隔离的内存 SQLite 连接检验 UTF-8、JSON 类型和重复必填键。库数据库则由文件只读连接打开。应用标识、schema、UUID 和其它元数据在同一个 SQLite 读事务中检查。`inspect` 返回的 `LibraryInspection.info` 可用于展示和诊断，连接在调用结束时释放。已启用 WAL 的数据库检查可能产生 SQLite 辅助文件，实测已记录其行为。[验证记录](../testing/P1.3_library_foundation.md)

`LibraryLease.acquire(root)` 先核对库，再用父目录下的稳定锁文件取得 Windows 独占句柄。锁文件名来自最终目录名。库在租约期间不能正常改名，同一库的目录联接会命中同一个锁。其他进程遇到共享冲突时收到可重试的 `LibraryBusy`。

`open(root, lock)` 先在互斥锁内取走租约，因此随后 `lock.valid` 为假。由卷和文件 ID 对比调用路径与租约，重读 UUID、格式和版本，并在只读连接上执行 `quick_check(1)`。这些检查通过后才建立 SQLite 写连接，启用 WAL 与 `synchronous=FULL`。连接按打开它的线程使用，会话的状态查询和关闭通过互斥锁串行化。`open` 失败时，已消费的租约随栈内资源释放。多次 `close()` 使会话保持关闭状态。

```python
from pathlib import Path
from _markdownshelf_core import Library, LibraryLease

created = Library.create(Path.cwd(), "工程资料")
checked = Library.inspect(created.root)
lease = LibraryLease.acquire(checked.info.root)
session = Library.open(checked.info.root, lease)
try:
    print(session.info.library_uuid, session.info.schema_version)
finally:
    session.close()
```

Python 绑定在持有 GIL 时转换参数，纯 C++ 阻塞操作期间释放 GIL。发生错误时，Python `LibraryError` 带有 `code`、`message_key`、`retryable`、`operation_id` 和 `recovery_path`。三项库操作当前是同步接口，后台作业和取消由 P1.6 接入。P2.1 负责登记和搬迁路径，P2.2 负责同 UUID 的跨路径协调和窗口激活，P4.9 负责保护快照和升级发布。
