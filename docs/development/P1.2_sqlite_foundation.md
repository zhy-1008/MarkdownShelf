## 打开连接与执行 SQL

`Connection(path, mode, busy_timeout_ms)` 接收 `std::filesystem::path`、打开模式和毫秒数。路径转成 UTF-8 后交给 `sqlite3_open_v2`。`read_only` 和 `read_write` 打开已有文件，`read_write_create` 也能创建文件。若 SQLite 以只读方式打开了要求可写的库，构造函数返回错误。锁等待默认 1,000 ms，传 0 表示遇到锁时立即返回。每次打开显式启用外键约束，避免连接之间的默认设置影响行为。

`configure_wal()` 在身份和版本检查后用于受信任的可写本地库。它先设 `synchronous=FULL`，再检查 `journal_mode=WAL` 实际返回的模式。WAL 设置会保存在库文件中，下一次打开可以读到。读连接可在延迟事务中持有读快照，写连接提交后，读事务结束才会看到新版。后续服务的串行写队列可以使用同一写连接，每个读取任务使用所属线程的连接。[SQLite WAL](https://www.sqlite.org/wal.html)

`prepare(sql)` 返回独占 `sqlite3_stmt` 的 `Statement`。SQL 为服务代码中的单条语句，值用 `bind_int64`、`bind_text`、`bind_null` 绑定到从 1 开始的参数索引。`bind_text` 传入显式长度，SQLite 复制数据，因此 UTF-8 字符和内嵌 NUL 均可按字节保留。空文本与 SQL NULL 分别用空字符串和 `std::nullopt` 表示。

`step()` 返回 `true` 时可以读取当前行。列索引从 0 开始，读取接口返回按值持有的 `std::optional`。`false` 表示执行完成，带 `RETURNING` 的写语句也应执行到该状态。`reset()` 清除已有绑定并重置语句，可能报告遗留的执行错误。需要执行多条固定 SQL 时用 `execute(sql)`，事务控制由 `Transaction` 负责。

连接、语句和事务均禁止复制及移动。语句和事务借用连接，使用同一线程，并在连接前销毁。构造失败也由独占句柄负责清理。SQLite 执行错误包装为 `SqliteError`，可通过 `extended_code()` 区分唯一约束、外键等子类，通过 `primary_code()` 判断 `SQLITE_BUSY` 等大类。错误对象记录操作名和 SQLite 错误类型，避免附带路径、SQL 文本或参数值。输入及调用顺序错误通过标准 C++ 异常报告。

## 事务何时结束

`Transaction(connection)` 默认执行 `BEGIN IMMEDIATE`，在写入前取得写锁。只读快照可显式选 `TransactionMode::deferred`。一次只允许一个事务对象持有该连接。同一作用域内先声明事务，再声明语句，析构顺序会先释放语句。

```cpp
Transaction write(connection);
{
    auto insert = connection.prepare("INSERT INTO notes VALUES (?1, ?2)");
    insert.bind_int64(1, id);
    insert.bind_text(2, title);
    insert.step();
}
write.commit();
```

`commit()` 成功后解除事务归属，析构无需再执行 SQL。若语句抛出异常或作业在提交前提前返回，析构检查 SQLite 的 autocommit 状态并回滚仍打开的事务。`INSERT OR ROLLBACK` 一类错误可能已经使 SQLite 完成回滚，这时只需清理 C++ 事务状态。延迟外键也可能在 `COMMIT` 才失败，`commit()` 会先回滚，再抛出原提交的 SQLite 错误。若回滚后事务仍然打开，连接被标记为不可继续使用，留给作用域退出关闭句柄。P1.2 的提前退出由作用域管理，后台作业取消协议由 P1.6 接入。[SQLite autocommit](https://www.sqlite.org/c3ref/get_autocommit.html)

## 迁移的提交边界

`migrate_schema(connection, migrations)` 接收从版本 1 起的完整 `std::vector<Migration>`。每项含目标版本号、借用的 SQL 字符串，以及可选的 `void (*)(Connection &)` 数据转换。SQL 字节须在调用期间有效，转换同步使用当前连接。调用方提供已隔离的库文件并负责其身份、备份和发布。

执行前先验证迁移序列，通过 `schema_version()` 读取 `PRAGMA main.user_version`。当前版本等于目标时直接返回，较新的版本抛出 `SchemaTooNew`。准备升级时，在 `BEGIN IMMEDIATE` 取得写锁后重读版本，避免按锁外读到的旧版本重复执行步骤。

每一步先执行 SQL 和数据转换。该段用 SQLite authorizer 阻止脚本自带事务命令、附加数据库和自行写 PRAGMA。FTS5 使用的只读 `data_version` 允许通过。执行结束后检查外键，再由迁移入口更新 `user_version`，最后提交。第二步若在创建表或写入数据后失败，第二步的 DDL 与数据一起回滚，先前提交的步骤已留在暂存库，重试从对应版本继续。按版本分步提交符合 §8.3 的暂存库流程，也让重试位置可从数据库本身查到。

## FTS5 如何发现 tokenizer

`register_fts5_tokenizer(connection, name, tokenizer)` 接收当前连接、注册名和 `fts5_tokenizer` 的三个 C 回调。`SELECT fts5(?1)` 的参数用 `sqlite3_bind_pointer` 传入 `fts5_api*` 的地址，执行后 SQLite 写入当前连接的 API 指针。`xCreateTokenizer` 复制回调表，同名注册会被拒绝。当前接口支持无注册上下文的工厂，每次 `xCreate` 建立的实例由 `xDelete` 清理，回调通过 SQLite 结果码报告错误。

测试用 tokenizer 把整段输入作为一个 token。注册后 `"std::vector"` 能命中，`vector` 得不到命中，证明索引和查询都执行了自定义回调。重开连接后索引仍在，`MATCH` 执行需要在该连接注册同一名称。正式分词规则与字典由后续搜索功能实现。[SQLite FTS5 自定义 tokenizer](https://www.sqlite.org/fts5.html#custom_tokenizers)

## 调试入口

构建 Debug 后可直接用 GoogleTest 过滤器运行相应场景。在 `Transaction::commit` 和 `Transaction::rollback` 设断点，运行外键失败用例，可以观察 COMMIT 错误后连接如何恢复到 autocommit。迁移失败可在 `apply_step`、`authorize_migration`、`schema_version` 断点观察 DDL 和版本号的边界。

```powershell
ctest --preset win-x64-debug -R 'FailedCommit|FailedMigration|CustomTokenizer'
build/win-x64-debug/markdownshelf_core_tests.exe --gtest_filter=SqliteTest.FailedCommitRollsBackDeferredForeignKeyViolation
```

如果测试库能建 FTS5 虚表但重连后的 `MATCH` 报错，先检查该连接是否注册了创建虚表时使用的名字。遇到 `SQLITE_BUSY` 时检查当前事务持锁位置、调用方配置的等待时间，以及读任务是否及时结束快照。
