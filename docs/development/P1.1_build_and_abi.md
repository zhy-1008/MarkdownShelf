## 从 Python 调用到 C++

1. `import _markdownshelf_core` 在暂存目录定位 `.pyd`。Windows PE 加载器先解析 DLL 依赖，CPython 再调用 `PyInit__markdownshelf_core`，由 `PYBIND11_MODULE` 注册函数。
2. `probe(text: str) -> dict` 的绑定参数是 `const py::str &`。该借用只在本次调用中有效，`noconvert()` 要求 Python 字符串类型，整数和字节串会在进入核心前得到 `TypeError`。
3. `text.cast<std::string>()` 按 UTF-8 复制到 C++ 所拥有的字符串。`markdownshelf::probe(std::string text)` 按值接收，可带空字符串或内嵌 NUL。`std::move` 把该字符串移动到返回值 `AbiProbeResult`。它的 `contract_version` 是 C++ `int`，本契约值为 1，`text` 是持有原始字节的 C++ 字符串。
4. 绑定把 `contract_version` 和解码得到的 `text` 放入 Python 字典，字典中的值由 Python 管理。整个调用同步完成，对 Python 对象的访问在持有 GIL 时发生。核心只进行值传递，任一步失败时局部对象随作用域清理。探针不产生外部状态，因此不存在任务取消或持久化回滚入口。

使用 `python -m pytest tests/python/test_abi_probe.py -k non_bmp` 可调试中文和非 BMP 用例。在 VS Code 使用原生调试器启动当前虚拟环境的 `python.exe`，参数设为上面的 `-m pytest …`，工作目录指向仓库，`PYTHONPATH` 指向与构建配置一致的暂存根。在 `module.cpp` 的 lambda 或 `abi_probe.cpp` 的 `probe` 打断点。保留构建目录中的 PDB，必要时从该目录加载符号。

## 区分失败发生的阶段

- **配置或链接阶段**。CMake 根据同一 CPython 安装解析解释器和扩展开发组件。Windows x64、MSVC v143、Python 3.12 的检测结果可从配置输出和缓存复查。配置失配时用正确环境在新的构建目录重试。
- **模块加载阶段**。使用 `dumpbin /headers` 检查 PE 架构，用 `dumpbin /dependents` 确认 Python 和 CRT 依赖。隔离子进程的 `-I -S` 排除 `PYTHONPATH` 与站点初始化，pytest 验证没有暂存入口时得到指向模块名的 `ModuleNotFoundError`。
- **入参转换和结果阶段**。绑定拒绝非字符串输入。对合法 Unicode，pytest 核对 C++ 到 Python 的完整往返，包括空字符串、中文、非 BMP 及内嵌 NUL。GoogleTest 可独立确认 C++ 看到的字节值。
- **依赖校验阶段**。CMake 为下载和本地缓存使用同一个 SHA-256，pip 用 `--require-hashes` 校验 wheel。内容有误时换回匹配归档，并从独立构建和暂存路径复测。工具链和依赖锁定用于复现配置及测试行为，PE 文件是否逐字节相同属于不同的验证目标。

## Windows Debug 实测

首次配置的编译探测中，MSVC 使用 `/Zi` 写编译阶段的 PDB，报告 C1902。预设通过 CMake 3.25 的调试信息格式选择，在 Debug 下用 `/Z7` 将符号先写到对象文件，链接时再生成 PDB。这样编译探测和一方 Debug 构建均可完成，仍可对绑定和核心打断点。

`dumpbin` 证实 Debug 和 Release 扩展都链接 `python312.dll`，并在同一个普通 CPython 3.12 x64 环境成功导入。Debug 仍需本机 Visual Studio 提供的调试 CRT，适用于开发调试。第 2.2 节的 `RelWithDebInfo` 回退条件未触发。

静态分析对一方目标启用 `/analyze`，CMake 传给 MSVC 的第三方系统头目录采用 `/analyze:external-` 范围。GoogleTest 的断言宏为避免悬挂 `else` 使用常量 `switch`，展开处在本项目测试源码中触发 C6326。`test_abi_probe.cpp` 用一对 `warning(push/pop)` 将 C6326 抑制限制在该文件的两个最小测试。其他一方源码继续使用 `/W4 /WX /analyze`。[MSVC 静态分析选项](https://learn.microsoft.com/en-us/cpp/build/reference/analyze-code-analysis)

## clangd 如何读取构建信息

Ninja 预设在 CMake 配置阶段导出 `compile_commands.json`。每个 C++ 源文件都有自己的编译器、标准、宏和头文件搜索路径。`module.cpp` 因此能解析 CPython 和 pybind11 头文件，`test_abi_probe.cpp` 则使用 GoogleTest 的搜索路径。[CMake 编译数据库](https://cmake.org/cmake/help/latest/variable/CMAKE_EXPORT_COMPILE_COMMANDS.html)

根目录的 `.clangd` 把项目数据库定位到 `build/win-x64-debug`。CMake 在 Developer PowerShell 中记下 `INCLUDE` 中的 MSVC 和 SDK 路径，并作为一方目标的系统头目录写入实际编译命令。普通 VS Code 进程即使未继承该终端的环境，也能用数据库解析 `<string>` 等头文件。路径取自配置时的工具链环境，记录在各配置的本地构建目录里。[clangd 编译参数](https://clangd.llvm.org/config#compileflags)

工作区配置沿用后台索引、clang-tidy 和详细补全，由 `.clangd` 选库，并关闭此工作区的微软 C/C++ IntelliSense。后台索引处理项目源码，遇到 `build/<预设>/_deps` 下的依赖源码时跳过独立索引，一方翻译单元仍会解析其引用的依赖头。GoogleTest 源文件的 C6326 pragma 条件只对 MSVC 生效，使 clangd 也能解析同一个翻译单元。复现编辑器入口时，在 `src/bindings/module.cpp` 对 `markdownshelf::probe` 执行“转到定义”，应定位到 C++ 核心。验证细节见[测试记录](../testing/P1.1_build_and_abi.md#clangd-工作区验证)。
